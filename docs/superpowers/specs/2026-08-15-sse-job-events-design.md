# FileButler SSE 任务事件与即时刷新设计

日期：2026-08-15

## 目标

用一条经过登录校验的 Server-Sent Events（SSE）连接替代当前所有任务状态轮询，使文件操作和任务面板具有以下行为：

- 后台任务尚未结束时，文件面板不因任务进度变化而刷新；
- 任务进入终态后，相关完成通知立即触发文件面板刷新；
- 任务列表、活动任务数量和已选任务详情由事件驱动更新；
- 网络中断期间不启动后备轮询，恢复连接后通过快照收敛到数据库中的真实状态；
- 重命名等短任务即使在创建接口返回前完成，也不会漏掉刷新。

## 已确认行为

- 保留现有 REST 接口用于创建任务、取消任务、读取任务详情和其他普通请求。
- 新增一条全局任务 SSE 连接，不把全部 REST API 改造成 WebSocket 或其他 RPC 协议。
- 删除 `DualPane` 中每秒查询单个任务的完成轮询。
- 删除 `JobsSheet` 中每两秒刷新列表和每秒刷新详情的轮询。
- `pending`、`running`、`cancel_requested` 只更新任务界面，不刷新文件面板。
- `completed`、`completed_with_errors`、`failed`、`canceled` 都视为终态。任何终态都刷新文件面板，因为失败和取消前也可能已有部分文件变更。
- 首次连接和每次重连都接收任务快照。断线期间完成的任务在重连后立即补刷新。
- 不提供低频轮询兜底。现有文件面板手动刷新按钮继续保留。

## 架构决策

采用“SQLite 作为事实来源、持久事件版本负责断线游标、进程内事件代理负责低延迟通知、SSE 快照负责恢复”的结构：

1. 任务状态先成功提交到 SQLite。
2. 同一数据库事务为本次变化分配新的全局事件版本。
3. `jobs.Store` 在提交后向进程内事件代理发布结构化任务事件。
4. `/api/jobs/events` 将快照和实时事件写入 SSE 流。
5. 前端只建立一个任务事件连接，并在共享任务状态中合并事件。
6. 文件面板只订阅去重后的终态通知。

事件代理不是事实来源。连接断开、订阅者过慢、服务进程重启或某条实时事件未送达时，客户端下一次连接读取 SQLite 快照恢复状态，因此正确性不依赖事件代理永久保存历史。

## 持久事件版本

新增单行事件计数表 `job_event_clock(id, version)`，固定使用 `id = 1`；同时为 `jobs` 表增加非空整数列 `event_version`，已有任务迁移为 `0`，事件计数从 `0` 开始：

- 每次任务状态变化都在同一事务中将全局计数加一，并把新值写入该任务的 `event_version`；
- 全局事件版本在服务重启后继续递增；
- 同一个任务后发生的变化必然拥有更大的事件版本；
- 前端以 `(job.id, job.eventVersion)` 判断事件新旧和去重，不依赖秒级 `updated_at` 时间戳；
- SSE 使用同一个事件版本作为持久断线游标，不维护另一套内存序号。

以下写操作都会生成新的事件版本并在提交后发布事件：

- 创建任务；
- 标记为运行中；
- 请求取消；
- 记录一个条目结果并增加进度；
- 写入最终状态。

状态更新同时收紧为条件更新：只有 `pending` 可以进入 `running`，只有非终态任务可以进入 `cancel_requested`，而终态任务不再被迟到的取消请求覆盖。这样取消请求和任务自然完成发生竞态时，数据库中的终态仍然稳定。未改变状态的幂等请求不分配新事件版本，也不发布事件。

现有的“写入条目结果”和“增加进度”合并为同一个事务操作。这样任务条目、`progressDone` 和事件载荷始终对应同一次已提交状态，不会出现进度已经推送但条目尚未写入的中间状态。

## SSE 协议

### 端点

新增受现有 Cookie 会话中间件保护的端点：

```text
GET /api/jobs/events
```

成功响应至少包含：

```text
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
X-Accel-Buffering: no
```

处理器必须支持 `http.Flusher`，写入每个事件后及时刷新缓冲区。连接建立时发送 `retry: 2000`，使浏览器断线后约两秒重试。每十五秒发送一条 SSE 注释心跳，避免空闲连接被反向代理提前关闭。

### 快照事件

每次连接建立后首先发送：

```text
event: jobs.snapshot
id: <event-version-watermark>
data: {"cursor":<event-version-watermark>,"jobs":[...]}
```

快照包含：

- 所有非终态任务；
- 最近五十个终态任务；
- 当请求带有有效 `Last-Event-ID` 时，所有 `event_version` 大于该游标的任务，即使它们不在最近五十个终态任务中；
- 每个任务当前的 `eventVersion`、状态、进度、根目录和时间字段。

包含所有非终态任务可以防止运行时间较长的任务被“最近五十条”限制排除。包含游标之后变化过的全部任务，则保证长时间断线期间即使完成超过五十个任务，也不会漏掉较早的终态变化。重复出现在多个集合中的任务按 ID 合并，并按创建时间从新到旧排列。

`Last-Event-ID` 只接受非负十进制整数。缺失或格式无效时按首次连接处理，不根据游标扩展终态集合。

### 实时任务事件

每次任务状态提交后发送：

```text
event: job.changed
id: <job.eventVersion>
data: {"job":{...},"item":{...}}
```

- `job` 是提交后的完整任务摘要；
- `item` 只在某个任务条目刚刚执行完成或失败时出现；
- 创建、运行、取消请求和最终状态事件不需要 `item`。

SSE 事件 ID、任务的 `eventVersion` 和数据库全局事件版本是同一个值。浏览器自动携带的 `Last-Event-ID` 只用于决定快照必须补回哪些任务；服务端不回放内存事件历史，也不会因为存在游标而跳过权威快照。

## 无丢失的连接建立顺序

SSE 处理器按以下顺序建立流：

1. 在事件代理中注册带缓冲的订阅者；
2. 在一个一致的 SQLite 读事务中读取当前全局事件版本作为快照水位，并查询任务快照；
3. 将带水位事件 ID 的快照写入并刷新；
4. 依次发送订阅后进入缓冲区且事件版本大于快照水位的实时事件；
5. 继续等待实时事件、心跳或请求上下文结束。

“先订阅、后查询快照”保证查询期间发生的任务变化不会丢失。某个提交后的发布动作可能晚于快照读取，因此缓冲区中也可能出现事件版本不大于水位的事件；处理器直接丢弃这些已被快照覆盖的事件，前端仍会按任务事件版本进行第二层去重。

每个订阅者使用有界缓冲区。若浏览器或网络长期过慢导致缓冲区溢出，事件代理主动关闭该订阅，而不是静默丢弃事件；浏览器随后自动重连并用新快照恢复。

## 后端组件设计

### 任务事件代理

在 `internal/jobs` 中增加并发安全的事件代理，职责仅包括：

- 注册和注销订阅者；
- 将已经带有持久事件版本的事件广播给当前订阅者；
- 在订阅者缓冲区溢出时终止该订阅。

代理不查询数据库、不执行业务逻辑，也不决定哪些状态应刷新文件面板。

### 任务存储

`jobs.Store` 接收一个可选事件发布器。测试或不需要实时事件的调用方可以不配置发布器，存储行为保持可用。

所有事件版本分配和任务写入都发生在同一个数据库事务中，发布发生在事务提交成功之后。数据库写入失败时不得发送事件。存储层负责返回提交后的任务摘要以及可选条目结果，避免运行器自行拼装可能与数据库不一致的载荷。

### 任务运行器

`jobs.Runner` 继续负责状态推进和条目执行，但改用原子“记录条目结果并增加进度”存储方法。运行器不直接操作 SSE 连接，也不感知前端订阅者。

### SSE 处理器

处理器负责：

- 验证客户端已登录；
- 建立订阅并查询快照；
- 编码具名 SSE 事件；
- 定时发送注释心跳；
- 在请求取消、写入失败或订阅溢出时清理资源。

端点沿用当前任务 API 的可见性规则。本次改动不同时重定义多用户任务隔离策略。

## 前端组件设计

### 共享任务事件状态

在已登录工作区生命周期内只创建一个原生 `EventSource`。共享任务状态负责：

- 维护按任务 ID 归一化的任务摘要；
- 合并 `jobs.snapshot` 和 `job.changed`；
- 按 `eventVersion` 忽略重复、乱序或旧事件；
- 计算活动任务数量和任务筛选列表；
- 保存实时到达的任务条目增量；
- 暴露 `connecting`、`connected`、`reconnecting` 状态；
- 记录本浏览器刚创建的任务 ID；
- 记录所有已经处理过的终态事件版本；
- 每次事件合并批次只要包含一个或多个未处理终态，就发出一次文件变化通知。

快照作为一个批次处理，因此一次重连无论补回多少终态都只触发一次目录刷新。状态合并和终态通知完成后，共享缓存保留全部非终态任务以及最新五十个终态任务；仅用于游标补偿的更旧终态不会长期留在任务列表中。当前已选详情如果被列表裁剪，可以保留到用户选择其他任务或关闭任务面板。

组件卸载或用户离开已登录工作区时关闭 `EventSource`。

### 文件面板刷新

`DualPane` 不再按任务 ID发起完成查询。任务创建成功后只执行：

- 清除选择；
- 显示“任务已创建”提示；
- 将返回的任务 ID 注册到共享任务状态。

共享状态收到新终态事件版本后立即通知 `DualPane`。`DualPane` 刷新左右两个面板，保持当前安全行为，不尝试根据根目录猜测某个面板一定不受影响。

如果前一次终态刷新仍在请求文件列表，又收到新的终态事件批次，则标记一次待刷新状态；当前刷新结束后再执行一次，不使用定时器，也不会为同一事件版本重复刷新。这样既避免并发旧响应覆盖新数据，也不会漏掉连续完成的任务。

### 任务面板

`JobsSheet` 改为读取共享任务状态：

- 列表、进度、状态和活动任务数量直接由快照及实时事件更新；
- 打开某个历史任务详情时允许调用一次 `GET /api/jobs/{id}` 获取完整已有条目；
- 后续条目通过 `job.changed.item` 增量合并；
- 重连快照显示已选任务在断线期间发生过变化时，允许再调用一次详情接口补齐可能错过的条目；这属于重连对账，不是周期轮询；
- 选中任务进入终态时不需要再次轮询；
- 取消仍使用现有 REST 接口，状态变化由 SSE 返回；
- 连接中断时在任务面板描述区域显示克制的“正在重新连接”状态，不弹出重复错误提示。

前端新增与后端 `ItemResult` 一致的 `JobItem` 类型。失败条目根据 `status === "failed"` 显示 `errorMessage` 或 `errorCode`，不再把任务执行结果误当成预览阶段的 `PlanItem`。

## 终态通知与竞态处理

### 首次快照

首次快照建立当前任务基线，不为历史终态任务批量刷新文件面板。文件面板自己的首次目录读取负责展示当前文件系统状态。

### 创建接口返回前已完成

短任务可能在 `POST` 创建接口返回前就进入终态：

- 若实时终态事件先到，共享状态立即刷新并记录该终态事件版本已通知；
- 随后注册创建任务 ID 时不会重复刷新；
- 若事件连接尚未建立，注册 ID 后发现当前快照中任务已经终止，则立即刷新。

### 断线期间完成

共享状态保留断线前已知的任务事件版本和状态。重连快照到达时：

- 已知活动任务变为终态：立即补刷新；
- 本浏览器已注册但此前未知的任务已经终止：立即补刷新；
- 重连后首次出现的新终态任务：视为断线期间可能发生的文件变化，刷新一次；
- 已通知过的相同终态事件版本：忽略。

这套规则提供至少一次终态通知语义，实际文件刷新是幂等操作，因此重复传输不会造成错误。

## 网络和代理行为

- 弱网或临时断网不会影响后台任务执行，因为任务运行不依赖 SSE 连接。
- 断线时任务界面可能短暂保持旧状态，这是预期行为；恢复后由快照纠正。
- 不启用隐藏轮询，因此长时间离线时只能通过重新连接或用户手动刷新文件面板获得新状态。
- SSE 心跳只维持连接和帮助发现断线，不触发任务查询或文件刷新。
- 禁止代理响应转换和缓冲，部署文档需保留 `text/event-stream` 的流式传输。

## 错误处理

- 快照查询失败：结束当前 SSE 响应，让浏览器按重连策略重试。
- 单次事件写入失败：清理订阅并结束处理器。
- 订阅缓冲溢出：主动断开，依靠新快照恢复。
- 无效或旧事件版本：客户端静默忽略。
- 详情 REST 请求失败：保留已有摘要和实时进度，允许用户重新选择任务后重试，不启动轮询。
- 会话失效：SSE 无法重新建立；现有认证流程负责用户重新登录。本次不新增独立令牌机制。

## 测试设计

### 后端单元和处理器测试

- 任务创建、运行、取消、进度和终态写入各自分配新的持久事件版本，并且只在提交成功后发布事件。
- 服务重启后事件版本继续递增，`Last-Event-ID` 之后变化过的任务不会受最近五十条限制。
- 条目结果与进度在一个事务中更新，事件同时包含匹配的任务摘要和条目。
- 事件代理按序广播并正确注销订阅者。
- 订阅者缓冲溢出会关闭订阅而不是静默丢事件。
- SSE 端点拒绝未登录请求，并返回正确的流式响应头。
- 连接后的第一条业务事件是 `jobs.snapshot`。
- 在快照查询期间产生的实时事件最终仍会发送。
- 心跳不会产生任务状态变化。
- 首次快照包含全部活动任务及最近五十个终态任务；重连快照还包含游标之后变化过的全部任务。

### 前端单元和组件测试

- 首次快照更新列表和活动数量，但不因历史终态任务刷新文件面板。
- `running` 和进度事件更新任务界面但不刷新目录。
- 每个新的终态事件版本立即且只刷新一次左右面板。
- 重复或乱序事件版本不会回退状态，也不会重复刷新。
- 创建接口返回前到达的终态事件不会漏刷新或重复刷新。
- 断线前活动、重连后终态的任务会由快照补刷新。
- 断线期间新建并完成的任务会在重连后刷新。
- 一个重连快照补回多个终态时只触发一次文件刷新，处理后终态列表仍限制为最近五十个。
- `JobsSheet` 不再创建 `setInterval`，列表和进度由事件更新。
- 选择任务详情只发起一次详情请求，后续条目由事件增量合并。
- 取消请求后的 `cancel_requested` 和最终 `canceled` 状态由事件反映。
- 组件卸载时关闭 `EventSource`。

### 集成和浏览器测试

- 执行单文件重命名，服务器完成后无需等待一秒即可看到新文件名。
- 长任务运行期间多次进度更新不会触发文件列表请求；进入终态后才刷新。
- 浏览器离线期间完成任务，恢复网络后由重连快照更新任务面板并刷新文件列表。
- 网络请求记录中不存在周期性 `/api/jobs` 或 `/api/jobs/{id}` 请求。
- Go 测试、前端测试、类型检查、生产构建和相关 Playwright 场景全部通过。

## 非目标

- 将全部 FileButler API 迁移到 WebSocket。
- 监听 FileButler 之外的进程直接修改文件系统。
- 为任务事件建立永久事件日志或提供任意时间点的历史事件回放。
- 支持多个 FileButler 服务实例之间的事件广播；当前架构仍为单服务进程配合单个 SQLite 数据库。
- 在服务重启后自动恢复被中断的运行中任务。
- 改变现有多用户任务可见性和授权规则。
- 添加系统通知、后台推送或浏览器标签关闭后的通知。
- 重新设计文件面板或任务面板的整体视觉样式。

## 验收标准

- 项目中不再存在用于查询任务完成状态、任务列表或任务详情的周期性轮询。
- 后台进度未完成时，文件面板不会因任务状态更新而刷新。
- 任一任务进入终态后，文件面板在收到事件时立即刷新，无固定一秒等待。
- 重命名等极短任务即使先完成、后返回任务 ID，也能可靠刷新。
- SSE 断线不会影响后台任务；重连后快照能补齐断线期间的状态和文件刷新。
- 任务列表、活动数量、进度、取消状态和最终状态均可在不轮询的情况下更新。
- 重复事件、乱序事件和重连快照不会导致状态回退或同一终态反复刷新。
- 现有任务 REST 接口继续可用，其他文件操作和认证行为保持兼容。
