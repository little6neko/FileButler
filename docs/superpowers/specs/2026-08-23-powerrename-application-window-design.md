# PowerRename 独立应用窗口设计

日期：2026-08-23
状态：已批准

## 概述

完整模式中的 PowerRename 从页面级模态框升级为真正的桌面应用窗口。用户可以从任意文件管理器窗口的顶部操作栏或右键菜单创建新的 PowerRename 窗口；每个窗口固定启动时的来源根目录和有序文件选择，拥有独立草稿、预览、窗口状态及任务栏按钮。

精简模式继续使用现有单个 PowerRename 弹窗。完整模式与精简模式共用 PowerRename 主体、后台重命名任务和右侧任务弹窗，但不在 PowerRename 窗口内重复显示任务进度。

本设计修订 `2026-08-22-web-desktop-multi-window-design.md` 中“首版只有文件管理器应用窗口”和“批量重命名保持页面级弹窗”的限制；其余桌面设计继续有效。

## 目标

- 在完整模式中允许同时打开任意数量的 PowerRename 应用窗口。
- 每次调用都创建并聚焦一个新实例，不复用已有 PowerRename 窗口。
- 让文件管理器和 PowerRename 共用窗口移动、缩放、层级、最小化、最大化、关闭及任务栏行为。
- 打开时捕获稳定的来源快照，使来源文件窗口之后的导航、改选、最小化或关闭不影响 PowerRename。
- 保留现有预览、冲突检查、选项默认值和“提交后只返回任务 ID”的后台任务流程。
- 保持精简模式现有弹窗体验，并在两种模式之间复用同一套 PowerRename 表单实现。
- 隔离多个实例的表单、异步预览和键盘行为，避免互相覆盖或误操作文件窗口。

## 非目标

本次不包含：

- 把普通重命名、新建文件夹、操作预览、媒体预览或任务中心改成桌面应用窗口。
- 向 PowerRename 窗口拖入文件以修改其项目列表。
- 在 PowerRename 窗口内显示后台任务进度或任务历史。
- 刷新后恢复 PowerRename 窗口、草稿、位置或预览。
- 把 PowerRename 草稿写入后端、SQL、`localStorage` 或其他持久化介质。
- 改变重命名后端 API、任务 SSE 协议或右侧任务弹窗的既有汇总更新策略。

## 已确认的产品行为

### 来源快照

创建 PowerRename 时捕获：

- 当前真实根目录的 `rootId`；
- 当前选择存储中的有序相对路径列表；
- 用于窗口标题和辅助信息的来源目录名称；
- 当时的全局 PowerRename 默认选项副本。

快照创建后不再绑定来源 `BrowserSession`。来源窗口改选、切换目录、最小化或关闭都不会改变该 PowerRename 实例。项目列表在此窗口生命周期内固定，也不接受文件拖放追加。

只有位于真实根目录且选择不为空时才能创建 PowerRename。虚拟“所有位置”页面继续禁用该操作。

### 模式边界

- 完整模式：每次点击文件窗口操作栏的 PowerRename 或右键菜单中的 PowerRename，都创建一个新的应用窗口。
- 精简模式：继续打开当前单个页面级 PowerRename 弹窗，不产生自由窗口或额外任务栏按钮。
- 从完整模式切到精简模式：隐藏桌面及所有桌面窗口，保留 PowerRename 草稿、窗口矩形和普通/最大化/最小化状态。
- 切回完整模式：恢复原有窗口集合，并重新校验可见 PowerRename 的预览；活动窗口仍按现有模式转换规则切到精简模式当前活动栏对应的文件窗口。

完整模式中的多个 PowerRename 窗口可以来自同一文件窗口、不同文件窗口或相同路径选择；它们始终是彼此独立的实例。

### 提交与关闭

- 标题栏关闭按钮和底部“取消”都会关闭当前 PowerRename 窗口并丢弃该实例草稿。
- “重命名”仅在最新选项的预览已成功完成且没有冲突时启用。
- 提交期间按钮进入忙碌状态并阻止重复提交；最小化或切换模式不会重置该状态。
- 创建任务请求未完成时禁用底部“取消”和标题栏关闭，避免请求已到达服务端但本地实例先被清理；窗口仍可最小化、最大化或随模式隐藏。
- 后端成功创建任务并返回任务 ID 后：提交当前选项为以后新实例的默认值，关闭且只关闭当前 PowerRename 窗口，并通过现有 `handleJobCreated` 打开右侧任务弹窗。
- 创建任务失败时：窗口保持打开，保留草稿并显示错误，用户可以修改后重试。
- 窗口关闭不会取消已经成功创建的后台任务；任务生命周期继续由后端和任务 SSE 管理。

## 窗口与应用状态架构

### 带类型的统一窗口记录

当前 `FileWindowRecord` 泛化为带判别类型的桌面窗口记录。所有类型共用几何和层级字段，业务内容只由对应应用解释：

```ts
type BaseWindowRecord = {
  id: string;
  status: WindowStatus;
  statusBeforeMinimize: RestorableWindowStatus | null;
  rect: WindowRect;
  restoreRect: WindowRect;
  zOrder: number;
  focusOrder: number;
};

type DesktopWindowRecord =
  | (BaseWindowRecord & {
      kind: "file";
      sessionId: string;
    })
  | (BaseWindowRecord & {
      kind: "powerRename";
      instanceId: string;
    });
```

窗口管理器只读取 `BaseWindowRecord` 字段。创建、聚焦、移动、缩放、最小化、恢复、最大化、关闭、MRU 回退及视口收敛对两种窗口使用同一套纯状态转换；它不请求目录，也不理解 PowerRename 业务数据。

现有 `openFileWindow` 可以成为通用创建操作的薄封装，PowerRename 使用对应的创建入口。新窗口沿用现有级联位置，创建后拥有最高 `zOrder`、最新 `focusOrder` 并成为 `activeWindowId`。

### PowerRename 实例注册表

PowerRename 业务状态独立于窗口几何，按 `instanceId` 保存：

```ts
type PowerRenameInstance = {
  id: string;
  rootId: string;
  paths: string[];
  sourceTitle: string;
  options: RenameOptions;
  submitting: boolean;
  submitError: string | null;
};
```

桌面域的“创建 PowerRename”转换同时加入实例和窗口记录；“关闭 PowerRename”同时移除两者，渲染期间不得出现孤立任务栏按钮或无主实例。文件窗口关闭仍按现有规则释放其浏览会话，PowerRename 关闭只释放自己的实例。

`options` 是受控草稿，因而在窗口最小化或模式切换导致内容卸载后仍能恢复。`submitting` 和 `submitError` 也属于实例状态：提交请求跨越卸载时仍只能存在一次，响应回来后仍能关闭实例或呈现失败。预览列表、加载状态和预览错误无需长期保留；窗口重新可见时根据固定快照和保存的选项重新请求，确保结果反映当前文件系统。

当前页面级 `powerRenameOptions` 继续作为“以后新实例的默认值”。创建实例时复制它，编辑某个实例不会影响其他已打开实例；只有该实例成功创建重命名任务时才更新全局默认值。多个实例先后成功提交时，以最后成功提交的选项为准。

## 组件设计

### 可复用 PowerRename 主体

现有 `RenameDialog` 拆分为两个层次：

- `PowerRenameContent`：表单、选项、预览表格、错误、提交状态和底部操作；不创建 `Dialog`，也不解释窗口几何。
- `PowerRenameDialog`：仅用于精简模式，用 `Dialog` 包装共享主体并保持当前模态行为。
- 完整模式直接在 `WindowFrame` 内渲染共享主体。

共享主体接收固定的 `rootId`、`paths`、受控 `options`、选项更新、提交状态、关闭和任务创建回调。桌面实例的任务创建请求由不会随窗口内容卸载而丢失的实例控制层协调；现有预览与提交 API 保持不变。

多个 PowerRename 可以同时挂载，因此当前固定的表单 ID（例如搜索、替换和预设列表 ID）必须改成实例作用域 ID，使用 React `useId` 或等价前缀生成。每个 `Label`、`Input`、`Checkbox`、组合框及其列表仍保持正确的可访问关联，DOM 中不得出现重复 ID。

### 桌面窗口渲染

`FileWorkspace` 按窗口 `kind` 分派内容：

- `file`：查找 `BrowserSession` 并渲染现有文件窗口。
- `powerRename`：查找 `PowerRenameInstance` 并渲染 PowerRename 主体。

所有读取 `BrowserSession` 的窗口派生逻辑都必须先筛选 `kind === "file"`，包括可见会话列表、活动会话、会话激活、后台任务后的目录刷新、文件会话引用计数，以及完整模式切换到精简模式时的 MRU 候选。PowerRename 不得成为精简栏绑定，也不得把 `instanceId` 当作目录 `sessionId` 使用。

`WindowFrame` 的窗口参数从文件专用类型改为基础窗口类型。PowerRename 获得与文件窗口一致的标题栏指针聚焦、移动、八方向缩放、双击最大化、最小化、恢复和关闭行为。

PowerRename 默认沿用现有级联尺寸策略。为保证双栏选项/预览可用，它可声明比文件窗口更大的应用级最小尺寸；当可用桌面不足时仍以可用边界为上限。最大化继续只占满任务栏以下的桌面区域。

PowerRename 窗口标题使用 `PowerRename — N 项` 的本地化计数形式。标题栏及任务栏按钮使用 `ScanText` 图标，与文件管理器的 `Files` 图标区分。每个未关闭实例都有单独任务栏按钮；点击、活动样式、最小化与恢复行为完全复用现有任务栏规则。

精简模式任务栏仍只显示固定的文件管理器按钮；隐藏的桌面 PowerRename 不在精简模式任务栏中出现。

## 预览与异步一致性

每个挂载的 PowerRename 主体只为自己的固定 `rootId`、`paths` 和当前 `options` 请求预览。每次请求使用递增世代号或 `AbortController`：

1. 选项变化后启动新预览，并使之前的预览不再满足提交条件。
2. 只有最新请求可以更新列表、冲突状态和错误。
3. 较慢的旧请求即使晚返回，也不能覆盖新选项的结果。
4. 组件卸载或实例关闭后忽略未完成响应。

恢复窗口时重新请求预览。若快照中的文件在此期间被移动、删除、重命名，或目标名称产生冲突，界面显示现有预览错误/冲突状态并禁止提交。即使预览成功，服务端在创建任务时仍是最终权威；提交阶段发现的变化按创建失败处理，窗口保持打开。

后台接口仍只需在创建成功后返回任务 ID。逐文件执行进度由现有内存任务存储、SSE 汇总事件和右侧任务弹窗负责，PowerRename 应用窗口不订阅或渲染第二份任务进度。

## 活动应用、快捷键与拖放

`activeSessionId` 只在当前活动桌面窗口的 `kind === "file"` 时指向浏览会话。PowerRename 成为活动窗口时，该值为 `null`，因此页面级 `Ctrl/Cmd+C`、`Ctrl/Cmd+X` 和 `Ctrl/Cmd+V` 不会落到此前活动的文件窗口。

PowerRename 输入框、复选框和预设控件保留浏览器常规键盘行为。现有 Enter 提交保护继续应用：只有表单可提交时才触发重命名，预设组合框处理中的 Enter 不得向外误提交。PowerRename 作为应用窗口时不依赖页面存在 `[role="dialog"]` 来阻止文件快捷键。

桌面 DnD 协调器只把 `file` 窗口注册为文件拖放表面。PowerRename 窗口可以像其他窗口一样参与视觉层级和命中遮挡，但不是文件放置目标，也不会因拖放悬停改变其固定路径快照。

## 模式转换和生命周期

桌面窗口集合在精简模式下继续保存在内存中。模式转换不关闭 PowerRename 实例、不清空选项或提交状态，也不改写窗口矩形或 `statusBeforeMinimize`。完整模式切到精简模式时，只从 MRU 文件窗口中选择左右栏绑定；活动 PowerRename 和其他应用窗口都不参与候选。切回完整模式后：

- 精简模式当前活动栏对应的文件窗口按现有规则恢复或创建并成为活动窗口；
- PowerRename 恢复原位置、尺寸、普通/最大化/最小化状态和草稿，但不覆盖上述文件窗口焦点；
- 可见 PowerRename 内容重新挂载并刷新预览；
- 最小化 PowerRename 保持最小化，直到用户从任务栏恢复。

页面刷新沿用现有完整模式规则：只持久化工作区模式，所有桌面窗口和 PowerRename 实例从空状态开始。已经在后端运行的任务仍会通过现有任务恢复/SSE 机制出现在右侧任务弹窗，这与 PowerRename 草稿持久化无关。

## 错误处理

- 快照创建前再次验证来源是实际目录且存在非空选择；条件不满足时不创建窗口。
- 找不到窗口引用的 PowerRename 实例时不渲染内容，并通过统一关闭转换清理孤立记录；正常实现路径应通过原子域转换避免此状态。
- 预览失败在当前窗口内显示，不影响其他实例。
- 预览冲突禁用当前窗口的提交，不影响其他实例。
- 创建任务失败保留当前草稿、快照和窗口状态。
- 创建任务请求期间即使内容因最小化或模式切换而卸载，实例级提交锁仍阻止第二次请求；失败信息在恢复后仍可见。
- 成功关闭一个实例时，仅清理该实例；不会关闭其他 PowerRename、释放来源浏览会话或取消任务。
- 根映射或文件系统在窗口打开后发生变化时，以预览和提交 API 返回的现有本地化错误为准。

## 测试与验收

### 窗口管理器单元测试

- 文件和 PowerRename 记录都能通过相同纯函数完成聚焦、移动、缩放、最小化、恢复、最大化和关闭。
- 所有几何转换保留窗口 `kind` 及业务引用。
- 新 PowerRename 获得最高层级并立即成为活动窗口。
- 关闭或最小化活动 PowerRename 后按 MRU 选择下一个可见窗口。
- 不同窗口类型的最小尺寸和视口收敛保持在可用桌面边界内。

### 工作区组件测试

- 同一文件窗口可连续创建多个 PowerRename，不同文件窗口也可同时创建实例。
- 操作栏和右键菜单都捕获点击当时的有序选择、`rootId` 和来源标题。
- 来源窗口导航、改选、最小化或关闭后，PowerRename 的快照不变且仍可预览和提交。
- 每个实例显示独立窗口、独立 `ScanText` 任务栏按钮和正确项目计数。
- 任务栏聚焦、最小化恢复、标题栏关闭及底部取消只作用于目标实例。
- 多个实例修改选项和收到乱序预览响应时互不影响，页面不存在重复表单 ID。
- 最小化/恢复和完整/精简模式往返保留草稿并重新校验预览。
- 精简模式继续使用单个模态框，且不显示完整模式 PowerRename 的任务栏按钮。
- 提交成功只关闭目标窗口、更新以后实例的默认选项并把任务 ID 交给现有任务流；失败保持窗口和草稿。
- 提交后立即最小化或切换模式不会产生重复任务；请求成功仍清理对应实例并注册任务，请求失败则恢复为可重试状态。
- PowerRename 活动时，文件复制、剪切和粘贴快捷键不会落到旧文件窗口；表单内键盘操作正常。
- 文件拖放不会把 PowerRename 当成目标，现有文件窗口之间拖放继续工作。

### 回归验证

- 现有 `RenameDialog`/PowerRename 选项、预览、冲突和提交测试迁移到共享主体后继续覆盖相同行为。
- 现有文件窗口、任务栏、完整/精简模式切换、上下文菜单和窗口间拖放测试继续通过。
- 前端单元测试、类型检查和生产构建通过。
- 后端任务、SSE 和 PowerRename 创建任务相关测试继续通过，确认前端窗口重构未改变任务协议。

## 实施边界

本次应优先复用现有 `WindowFrame`、窗口管理纯函数、`RenameDialog` 表单、API 客户端和任务事件存储，不引入第三方窗口框架或新的后端持久化。实现可以按“通用窗口模型”“共享 PowerRename 主体”“完整模式应用接入”“快捷键和模式回归”拆分提交，便于逐项验证和回退。
